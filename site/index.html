[BAP] Bounded Authority Protocol™

Bound authority.
Prove the exact request.

OAuth authorizes delegated, scoped access. Bounded Authority complements it with holder-bound grants naming permitted operations, argument bounds, audiences, and a validity window. The holder signs a proof binding the grant to the exact request context and canonical argument bytes. Pure verification returns cryptographic facts. The resource server still selects trusted keys, reserves replay, checks revocation, and applies its authorization policy.

Three properties, on purpose

Signed constraints let a service check the bounds before it acts. Audit evidence records what was verified.

Every capability is narrow.

OAuth scopes limit delegated access. A service may also need signed constraints on individual operations and argument values.

A grant is a signed, byte-frozen object naming operations, argument bounds, audiences, and a validity window. The proof binds the specific request target.

Every request is proven.

Replay and confusion attacks ride the gap between “authenticated session” and “this exact call.”

The holder's proof binds the method, target, invocation, grant, and digest of the operation and typed arguments. Changed context fails verification; repeated execution still requires the host's replay defense.

Trust is an explicit input.

Signature validity cannot decide which issuers a service trusts or whether a verified operation may execute now.

Already-trusted public keys and time are caller inputs. The verifier has no private-key access or custody and checks signatures and bindings offline, with deterministic, pure, closed results.
